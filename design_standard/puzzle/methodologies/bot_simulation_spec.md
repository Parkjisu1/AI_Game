# 봇 시뮬레이션 명세 — 퍼즐 장르 공용 검증 표준

> 레벨이 유효하고 의도한 난이도인지 자동 검증하는 표준.
> 정적 검증(난이도 점수) + 동적 검증(봇 플레이 클리어율) 2단계.
> 출처: BalloonFlow_봇시뮬레이션_명세 → 장르 일반화

---

## 1. 검증 2단계 구조

```
정적 검증 (Static — 큐/시퀀스 분석):
  생성된 레벨 → 난이도 점수(상대%) → 등급 추정
  → 이론적 추정. 실제 플레이 결과와 다를 수 있음

동적 검증 (Dynamic — 봇 시뮬레이션):
  레벨 → 최적 봇이 N회 플레이 → 클리어율 측정
  → 실제 플레이 기반. 단일 지표로 직관적
```

→ **정적 통과 → 동적 검증** 순서. 정적이 명확히 범위 밖이면 동적까지 가지 않고 재생성.

---

## 2. 최적 봇 (Perfect Play Bot)

### 2-1. 정의
**항상 최선의 선택을 하는 봇**. 봇의 클리어율 = 레벨의 이론적 난이도 상한.

### 2-2. 행동 패턴 (퍼즐 공통 골격)

```
매 턴 입력 단위 선택:
  1. 제거 가능한 대상 스캔 (예: 외곽 노출 색상)
  2. 큐/홀더에서 매칭 가능한 입력 탐색
  3. 매칭 가능 다수
     → 가장 많이 제거되는 옵션 선택
  4. 매칭 불가
     → 가장 안전한 옵션 선택 (자원 부담 최소화)

자원 위험 대응:
  - 자원 70%+ → 매칭 가능한 입력만 선택
  - 매칭 가능한 입력 없음 → 가장 작은 단위 선택

부스터:
  - 사용 안 함 (부스터 없이 클리어 가능한지 검증)
```

### 2-3. 왜 최적 봇 1종만?

- "일반 유저 행동"은 추정이지 팩트가 아님 (70% 매칭/30% 랜덤 같은 비율은 근거 없는 가정)
- 최적 봇 클리어율은 **객관적**. 같은 레벨이면 항상 같은 결과
- 난이도 해석이 단순. 클리어율 하나로 바로 판정
- 유저 행동 비교는 소프트런칭 데이터 확보 후로 미룸

> 단, **퍼즐 sub_genre별 행동 패턴 차이**는 봇 행동 내부 로직으로 흡수해야 함.
> 예: queue_sort=색상 매칭 / match3=인접 3+ 탐색 / merge=동일 등급 결합.

## 3. 클리어율 → 난이도 판정 (장르 표준)

| 최적 봇 클리어율 | 난이도 | 의미 |
|----------------|--------|------|
| 95~100% | Easy | 누구나 깰 수 있음 |
| 70~95% | Normal | 적당한 도전 |
| 30~70% | Hard | 상당한 도전 |
| 5~30% | Super Hard | 극한 도전 |
| 0~5% | **이상** | 레벨 유효성 의심 → 재설계 필요 |

> 최적 봇이 5% 미만이면 "최선의 플레이로도 거의 못 깬다" = 레벨 자체가 불공정.

---

## 4. 출력 지표 (모든 sub_genre 공통)

| 지표 | 설명 | 이상 판정 |
|------|------|---------|
| 클리어율 | N회 중 클리어 비율 | 목표 범위 밖 |
| 평균 턴 수 | 클리어까지 입력 횟수 | — |
| 자원 최대 도달량 | 가장 위험했던 순간 (%) | > 85% 빈번 |
| 실패 시점 | 실패 시 평균 몇 턴째 | 초반 실패 빈번 = 큐 앞쪽 문제 |

### 이상 징후 감지

| 조건 | 판정 | 대응 |
|------|------|------|
| 클리어율 < 5% | 유효하지 않은 레벨 | 큐/시퀀스 재생성 or 필드 수정 |
| 클리어율 목표 범위 밖 | 난이도 불일치 | 큐/시퀀스 재생성 |
| 평균 자원 도달량 > 85% | 실패 직전 빈번 | 입력 단위 max 또는 순서 조정 |

## 5. 시뮬레이션 파라미터

```yaml
trials_per_level: 100         # 빠른 검증. 통계적 충분
bot_count: 1                  # 최적 봇 1종
input_timing: turn_based      # 즉시 (실시간 아님)
booster_usage: false          # 순수 레벨 난이도 검증
fail_condition: <레벨별 정의>
```

소프트런칭 후 실제 유저 클리어율 데이터가 쌓이면, **최적 봇 클리어율 ↔ 실제 유저 클리어율 매핑 테이블** 작성. (예: 봇 70% ≈ 유저 50%)

## 6. 정적 난이도 점수 (Static Difficulty Score)

### 6-1. 상대 점수 공식 (sub_genre별 형태 다름, 골격 공통)

```
absolute = Σ <발사 불가/제거 불가 비용 × 단위 크기> / <자원 한도>
max_possible = <이 레벨에서 나올 수 있는 최대 difficulty>
relative = absolute / max_possible × 100%
```

→ 절대 점수가 아닌 **상대 점수**: "이 레벨에서 가능한 최악 대비 몇 %인가"
→ 필드 구조마다 max_possible이 달라도, 같은 relative = 같은 체감 난이도

### 6-2. 등급 매핑

| 상대 점수 | 등급 | 대응 purpose_type |
|----------|------|-----------------|
| < 35% | Easy | 튜토리얼, 휴식 |
| 35 ~ 70% | Normal | 노말 |
| 70 ~ 90% | Hard | 하드 |
| > 90% | Super Hard | 슈퍼하드 |

→ 정적 점수 적중률은 50~75% 수준. 동적 검증으로 보정.

## 7. 검증 워크플로우 (맵에디터 통합)

```
[Generate Queue/Sequence] 클릭
  ↓
정적 검증 (난이도 점수)
  ↓ 범위 내 (예: Normal 목표 = 35~70%)
[Simulate] 버튼 클릭
  ↓
최적 봇 N회 시뮬레이션
  ↓
결과 표시
  ↓
OK? → [Confirm] / 아님 → [Generate] 다시
```

### 결과 UI 예시
```
┌─ 봇 시뮬레이션 결과 ──────────────────────┐
│  클리어율: 73/100 (73%) → Normal ✅       │
│  평균 턴: 24 | 자원max: 68%               │
│  부스터: 미사용 (순수 레벨 검증)           │
│  [Confirm]          [Generate Again]      │
└────────────────────────────────────────────┘
```

## 8. AI 지시사항

1. **목표 클리어율 변경 시 Beat Chart의 §밸런스 검증 기준과 동시 업데이트**
2. **봇 행동 파라미터(자원 위험 임계 등)는 프로토타입에서 튜닝**
3. **5% 미만이면 자동으로 "유효하지 않은 레벨"로 분류**하여 디자이너에게 노출
4. **정적·동적 점수가 동시 통과해야 Phase 통과**. 한쪽만으로 판정 금지
5. **소프트런칭 후 실측 데이터 매핑 테이블 작성** — 봇 점수 보정용
6. **최적 봇 행동은 sub_genre마다 다름** — 행동 패턴 정의 시 명시적으로 작성
