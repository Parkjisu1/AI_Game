# 기계 검증 게이트 (fact gate)

산출물의 **기계로 판정 가능한 주장**을 LLM 없이 확인한다.
코더 → **게이트** → LLM 검수 순으로 끼워져 있고, dev 팀 태스크에만 적용된다.

## 왜 만들었나

2026-08-05 에 검수 지적을 성격별로 나눠 봤더니 대부분이 기계로 판정 가능한 것이었다.

| 지적 | 기계로 되나 |
|---|---|
| 인용 줄번호가 실제와 다르다 (3건) | 된다 — 파일을 열면 끝 |
| `git apply` 가 안 되는 잘린 패치 | 된다 — 적용해 보면 끝 |
| "저작권 문자열은 이 한 곳뿐" (실제 19곳) | 된다 — grep 하면 끝 |
| "razer 라벨 44개" (실제 42개) | 된다 — 세면 끝 |
| "근거로 든 테스트가 정반대를 단언한다" | **안 된다** — 판단이 필요하다 |

앞쪽이 압도적인데 전부 178초짜리 LLM 검수에 맡기고 있었다.
그래서 (a) 놓치기도 하고 (b) 판단에 써야 할 시간을 파일 대조에 쓴다.

## 설계 원칙: 판정하지 말고 해소하라

게이트는 좋고 나쁨을 말하지 않는다. **사실을 해소해서 표로 준다.**

- 인용한 줄을 실제로 열어 "그 줄에 뭐가 있는지" 보여준다
- 패치를 실제로 적용해 보고 되는지/안 되는지 말한다
- 산출물이 근거로 제시한 검색 명령을 다시 돌려 건수를 보여준다

"가서 확인해라"가 "여기 있다"로 바뀌면 검수는 대조가 아니라 판단에 집중한다.
맞다/틀리다 판정은 "그 줄이 무슨 내용이어야 하는가"를 알아야 하는데 그건 자연어라 기계가 모른다.

실제로 검수가 이렇게 썼다: *"Footer.tsx:128 인용도 기계 검증과 일치하고 패치도 적용 가능하다"*.

## 무엇을 검사하나

**1. 패치 적용** — `git apply --check` 를 plain 과 `--recount` 두 번 돌린다.
plain 실패 + recount 성공 = 헝크 헤더 줄 수만 틀린 것(고칠 수 있다).
둘 다 실패 = 내용이 안 맞는다.

세 경우를 구분한다:
- `truncated` — 코드블록이 닫히지 않았다. **하드 실패.**
- `illustrative` — `diff --git`/`@@` 가 없는 설명용 diff. 보고만 하고 판단은 검수자에게.
- 정상 — 통과.

> 이 검사가 왜 중요한가: 추출기는 형식이 어긋나면 **조용히 버린다**.
> 그래서 잘린 패치는 "패치 0건"으로 보고돼 아무 일도 없던 것처럼 보였다.

**2. 인용 해소** — `path:line` 을 실제 경로로 풀고 그 줄 내용을 보여준다.

경로 해소 순서가 중요하다:
1. 완전 경로 그대로
2. **접미사 일치** — `public/newplay/index.html` 은 유일하게 특정된다
3. 파일명만

2번을 3번보다 먼저 봐야 한다. 반대로 하면 파일명 조회가 정확한 인용을 덮어 모호로 만든다(실측: 못 푼 인용 4건 중 3건).

여전히 모호하면 **문서 자신의 문맥**으로 푼다 — 같은 문서가 앞에서 완전 경로로 쓴 적 있으면 그것으로.
산출물은 처음엔 `front-end/src/utils/constants.ts:255` 라 쓰고 뒤로는 `constants.ts:262` 로 줄여 쓴다.

**3. 전수 조사 재실행** — 산출물의 `## 전수 조사` 섹션에 적힌 검색 명령을 다시 돌린다.

전칭 주장("이곳뿐/전부/없다")은 자연어라 기계가 검증할 수 없다.
그래서 **주장 대신 명령을 요구한다** — 명령은 재현 가능하다.
부수 효과가 더 크다: 명령을 적어야 하니 코더가 실제로 찾아보게 된다.

안전장치는 넷이다. 셸을 쓰지 않고(`shell=False`) argv 로 실행, 실행 파일 화이트리스트
(`grep`/`rg`/`git grep`), 작업 디렉토리를 검증 트리로 고정, 절대 경로·`..` 차단.

> **한 번 틀렸던 부분**: 처음엔 원시 명령 문자열에서 셸 메타문자를 찾아 거부했다.
> 그러자 `grep -rn "a\|b" path` 같은 **정상 명령이 전부 거부됐다** — `\|` 는 grep 의
> BRE 교체 문법이고, 셸을 쓰지 않으니 애초에 해석되지도 않는다.
> 실제 산출물의 명령 5개가 전부 거부돼 검증 가치가 0 이 됐다.
> 검사는 **파싱된 토큰**에 해야 한다 — 따옴표 안의 문자는 셸 문법이 아니다.

```
- `grep -rn "rights reserved\|©" front-end/src`     → 3건
- `grep -rn "rights reserved\|©" front-end/public`  → 19건  ← "이곳뿐" 단정이 무너진다
- `rm -rf /tmp/whatever`                            → 실행 안 함 (허용되지 않은 명령)
- `grep ... | head -3`                              → 실행 안 함 (파이프는 토큰으로 남는다)
- `grep -rn x ../../etc`                            → 실행 안 함 (상위 경로 참조)
```

## 틀린 사실은 없는 사실보다 훨씬 나쁘다

이걸 실제로 겪었다. grep 은 기본적으로 바이너리 파일도 훑는다.
`grep -rln "…\|©" front-end/public` 이 **34건**을 냈는데 그중 15건이 png/webp 에서
`©` 바이트열이 걸린 것이었다. 정답은 19건.

게이트가 이 34 를 검수에 넘기자:

| 게이트 | 판정 | 지적 |
|---|---|---|
| 검색 결과 없음 | approve (80점) | 5건 |
| 검색 결과 있음 (34, **틀림**) | revise (62점) | 4건 — **그중 3건이 없는 불일치 위에 세워짐** |

검수는 "기계 검증 결과"라는 이유로 의심 없이 받아들이고 그 위에 전체 판정을 쌓았다.

두 가지를 동시에 말해 준다:
1. 게이트는 검수에 **강한 영향**을 준다 — 판정을 뒤집는다
2. 그래서 **정확도가 곧 전부다**. 사실을 내미는 도구가 틀리면 LLM 혼자일 때보다 나쁘다

대응: grep 실행 시 `-I`(바이너리 제외)를 자동으로 붙이고, 붙였다는 사실을 출력에 명시한다.

## 검증 대상 트리

`~/newplay-verify` — detached worktree. 갱신은 `refresh-verify-tree.sh`.

미리보기 빌드가 쓰는 `~/newplay-preview/webstore` 를 그대로 읽으면
빌드가 `git checkout` + `git clean -fd` 를 도는 동안 트리가 바뀌어 **틀린 사실**을 내놓는다.

**한계**: 이 호스트는 GitHub 자격이 없어 fetch 가 안 된다(deploy key 미등록).
레포는 떠 온 시점의 스냅샷이고, 그래서 게이트 블록은 항상 rev 와 날짜를 같이 출력한다 —
낡은 사실을 사실처럼 내미는 건 아무것도 안 내미는 것보다 나쁘다.
스냅샷을 갱신했으면 `refresh-verify-tree.sh` 실행 후 **워처 재시작**(파일 인덱스가 프로세스에 캐시된다).

## 아직 안 하는 것

- 산문에 쓰인 개수 주장("44개")은 검사하지 않는다. `## 전수 조사` 에 명령으로 적으면 건수가 대조된다.
- 하드 실패가 있어도 **자동으로 반려하거나 재작업을 돌리지 않는다.** 검수에 사실로 전달할 뿐이다.
  자동 재작업은 다음 단계다(실측 근거: 지적 6건을 되먹여 재작업하니 55점 → 91점).
