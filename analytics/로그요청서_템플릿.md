# 로그 요청서 템플릿

> **용도**: 신규 타이틀 출시 시 개발팀 메인 기획자가 직접 작성해 개발팀에 전달.
> **근거**: 사내 데이터 리터러시 가이드(로그 요청서 작성 참고용) + 우리 팀 퍼즐 공용 Raw Data Schema.
> **주의**: 회사 공식 "로그 요청서 템플릿"(다솜님 양식)을 받으면 그쪽을 기본 양식으로 쓰고,
> 이 문서는 **작성 시 빠뜨리기 쉬운 항목의 체크리스트**로 병행한다.

---

## 0. 문서 정보

| 항목 | 내용 |
|---|---|
| 게임명 | |
| 프로젝트 ID (GCP) | |
| 작성자 (메인 기획자) | |
| 작성일 / 개정일 | |
| 적재 방식 | ☐ 파이어베이스(테이블 1개, `event_name`으로 구분) ☐ 자체 서버(행동별 테이블 분리) |
| 데이터셋 주소 | `<프로젝트>.<데이터셋>` |

| 리전 | `asia-northeast3` (서울) |

> **적재 방식이 왜 중요한가** — 파이어베이스면 모든 이벤트가 `all` 테이블 하나에 들어가고 `event_name`으로 구분한다.
> 자체 서버면 행동마다 테이블이 따로 있어 여러 행동을 같이 보려면 붙여야 한다. 요청받는 쪽이 어디를 봐야 할지가 달라진다.

## 1. 공통 필수 컬럼 (모든 이벤트에 반드시 포함)

**이게 빠지면 그 로그는 어떤 데이터와도 붙일 수 없다.** 숫자는 쌓이는데 "누가 했는지"를 알 수 없어 분석이 불가능해진다.

| 컬럼 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `UID` (= `account_id`) | STRING | ✅ | **유저 식별자. 이게 없으면 결제·리텐션·UA와 못 붙인다.** |
| `session_id` | STRING | ✅ | 세션 단위 묶음 |
| `event_id` | STRING | ✅ | 이벤트 고유 ID (중복 적재 판별) |
| `event_timestamp` | TIMESTAMP | ✅ | 발생 시각 (UTC/KST 명시) |
| `game_id` | STRING | ✅ | 게임 구분 |
| `app_version` | STRING | ✅ | 빌드 버전 |
| `install_version` | STRING | | 최초 설치 버전 (코호트용) |
| `country` | STRING | ✅ | 국가 |
| `platform` | STRING | ✅ | iOS / Android |
| `device_model` | STRING | | 기기별 이슈 추적 |
| `campaign_id` | STRING | | **UA 데이터와 붙이는 키.** 광고 성과를 볼 거면 필수 |
| `server_id` | STRING | | 서버별로 볼 게임이면 필수 |

## 2. 이벤트 명세

이벤트마다 아래 표를 반복한다.

### 이벤트: `<event_name>`

| 항목 | 내용 |
|---|---|
| **1행 = 무엇 하나인가** | (예: 레벨 1회 시도 / 결제 1건 / 계정 1개) |
| 발생 시점 | 클라이언트의 어느 순간에 쏘는가 |
| 종류 | ☐ 로그(이벤트) ☐ 스냅샷(현황) |
| 기획 의도 | 이 로그로 무엇을 확인하려는가 |
| 확인할 지표 | (예: 레벨별 클리어율, 이탈 구간) |

**파라미터**

| 파라미터 | 타입 | 필수 | 값 예시 / 허용값 | 설명 |
|---|---|---|---|---|
| | | | | |

> **1행의 정체를 반드시 적는다.** 결제 테이블의 행 수는 결제 **건수**이지 결제한 유저 수가 아니다.
> 한 유저가 10번 결제하면 10행이다. "결제 유저 몇 명?"과 "결제 몇 건?"은 다른 질문이다.

## 4. 작성 전 자가 점검

작성자가 제출 전에 스스로 확인한다.

- [ ] 모든 이벤트에 `UID`가 들어가는가 — **하나라도 빠지면 그 이벤트는 분석 불가**
- [ ] 각 이벤트의 **1행이 무엇 하나인지** 적었는가
- [ ] 로그와 스냅샷을 구분했는가
- [ ] UA 성과를 볼 거면 `campaign_id`가 들어가는가
- [ ] 파티션 컬럼을 지정했는가 (없으면 전체 스캔 → 비용 폭증)
- [ ] 값이 코드/enum이면 **허용값 목록**을 적었는가 (`result`: clear/fail/cancel 처럼)
- [ ] 재화 변동은 **변동량과 변동 후 잔액**을 함께 남기는가
- [ ] 뽑기·상점 로그에 **그 시점의 보유 재화와 카운터**가 함께 남는가 (사후 복원 불가)
- [ ] 기획서에 "이 기능은 어떤 로그로 확인할지" 한 줄이 들어갔는가

> **로그는 사후에 만들 수 없다.** 출시 후 "이 지표 뽑아주세요"가 안 되는 이유의 대부분은
> 그 순간의 값을 안 남겼기 때문이다. 가챠 예시로 필요한 로그: 뽑기 시점의 재화 종류 / 보유 재화량 / 단차·연차 / 천장 카운트.

## 5. 분석 요청 시 관례 (요청하는 쪽이 지킬 것)

이 문서를 받는 사람이 나중에 지표를 요청할 때 붙여야 하는 네 가지.

**누구 / 언제 / 어떤 상황 / 어디**

- 나쁜 예: "시험의 탑 층별 승률이 어때?"
- 좋은 예: "최근 7일에 유입된 **신규 유저**의 시험의 탑 데이터 중 **첫 시도** 승률, **한국만**"

그리고 결제·매출 지표는 **"평균 말고 중위수랑 분위별로 같이 주세요"** 한 마디를 붙인다.
