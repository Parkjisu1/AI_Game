## 2. 이벤트 명세

### 2-1. `level_play_event` — **한 판 = 한 행** (핵심)

| 항목 | 내용 |

| 발생 시점 | 판 종료 시 (결과 확정 순간) |
| 종류 | 로그 |
| 기획 의도 | 레벨 난이도 검증, 이탈 구간 탐지, 아이템 의존도 확인 |
| 확인할 지표 | 레벨별 클리어율 / 평균 시도수 / 실패 사유 분포 / 아이템 사용률 |

### 2-2. `item_use_event` — 1행 = 아이템 사용 1회
판 단위 집계(`*_item_ids`)와 별개로 **개별 사용 상세**를 남긴다. 어떤 상황에서 썼는지 복원용.

### 2-3. `purchase_event` — 1행 = **결제 1건**
> ⚠️ 행 수 = 결제 건수. 결제 유저 수를 보려면 `COUNT(DISTINCT UID)`를 써야 한다.
> 매출 지표는 **평균 단독 금지** — 중위수와 분위(상위 1%/10%/중위/하위)를 함께 낸다.

### 2-4. `economy_event` — 1행 = 재화 변동 1건 (원장)
**변동량과 변동 후 잔액을 함께** 남긴다. 잔액만 있으면 원인을 못 찾고, 변동량만 있으면 현황을 못 만든다.

### 2-5. `session_event` — 1행 = 앱 세션 1회

### 2-6. `ad_event` — 1행 = 광고 시청 1회
보상형/전면 구분, 시청 완료 여부, 보상 지급 여부.

### 2-7. `user_property` — **스냅샷** (1행 = 유저 × 날짜)
> 로그가 아니라 **매일 그 시점의 상태**다. "지금"은 알 수 있지만 그 사이에 뭘 했는지는 모른다.
> 보유 재화·진행 레벨·누적 결제액 등.

### 2-8. `item_master` — 정의 테이블 (1행 = 게임 × 아이템)
`item_category`: `pre_play_item` / `in_play_item` / `continue_item` / `currency` / `consumable`

## 3. 이번 요청서에서 **추가로 요청할 항목**

기존 스키마에 없지만 가이드 기준으로 필요한 것들.

| 항목 | 이유 | 우선순위 |
|---|---|---|
| `campaign_id` (전 이벤트) | UA 캠페인별 성과 분해 (가이드 §02 축2) | 높음 |
| 누적 결제 분위 계산용 필드 또는 뷰 | 상위 25%/중위/하위 분해 (가이드 §02 축3) | 높음 |
| 상품군 구분 (`product_category`) | 월정액 / 패키지 / 가챠 재화 분해 (가이드 §02 축4) | 높음 |
| 뽑기 시점 스냅샷 | 뽑기 시점의 재화 종류·보유량·단차/연차·천장 카운트 — **사후 복원 불가** | 게임에 가챠가 있으면 필수 |
