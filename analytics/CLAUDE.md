# 팀 공용 추출 규칙

0. 이 폴더의 모든 BigQuery/데이터 작업은 아래 규칙을 반드시 따른다.

1. (필수·최우선) 첫 데이터 작업 전에 항상 아래 (a)(b)를 먼저 확인하고 이후 모든 추출에 적용한다. 둘 다 읽기 전용.
   (a) 해당 게임 "로그 요청서" 스프레드시트(구글 드라이브) — 이벤트/파라미터 세부 명세.
       위치를 모르면 게임 데이터 담당(다솜님)에게 요청해 링크를 이 파일에 적어둘 것: `<로그 요청서 링크 — 미수령>`
   (b) 팀 규칙 뷰 조회:
       ```sql
       SELECT content, rule_type
       FROM `<게임 프로젝트 ID>.<규칙 view 데이터셋>.<게임>_rules`
       ORDER BY rule_type
       ```
       -- rule_type 3종:
       -- game_extraction_rule: 해당 게임 추출 규칙 (테이블 구조, 유저 판별, 지표 정의)
       -- analysis_principle: 공통 분석 원칙 (cost-weighted 평균, cohort 정의, 확정 Dn 등)
       -- glossary_term: 공통 용어 정의 (ROAS/LTV/PU 등)

2. 규칙은 읽기 전용이다. 규칙 추가·수정·삭제는 사용자가 직접 처리한다.

빈 값으로 추측해서 쿼리를 짜지 않는다.

### 4. 질문을 먼저 좁힌다 (가이드 §01)

"승률이 어때?" 같은 요청은 **대상이 정해지기 전까지 실행하지 않는다.** 아래 네 개가 없으면 되묻는다.

- **누구** — 전체 / 신규만 / 특정 유입일차
- **언제** — 기간 (파티션 때문에 비용과 직결)
- **어떤 상황** — 첫 시도 / 재도전 포함
- **어디** — 국가·플랫폼·서버

같은 주제라도 대상이 달라지면 답이 정반대로 나온다. 고레벨 유저를 포함하면 상위 층 승률이 높게 나오고, 신규만 보면 같은 층이 벽으로 보인다.

### 5. 원인은 세그먼트로 쪼개서 찾는다 (가이드 §02)

"매출 15% 하락" 같은 전체 수치는 **아직 정보가 아니다.** 최소 아래 4축으로 쪼개 어느 덩어리가 빠졌는지 지목한 뒤 보고한다.

| 축 | 나누는 기준 |
|---|---|
| 유입 일차 | 3일 이내 / 3~7일 / 7~30일 / 30일 이상 |
| UA 캠페인 | 오가닉 / 캠페인별 |
| 누적 결제 분위 | 상위 25% / 중위 50% / 하위 25% |
| 상품군 | 월정액 / 패키지 / 가챠 재화 |

### 6. 평균을 단독으로 보고하지 않는다 (가이드 §03)

과금은 극단적으로 쏠려 있어 평균이 나머지를 지운다. 결제·매출 관련 지표는 **항상 중위수와 분위(상위 1% / 10% / 중위 / 하위)를 함께** 낸다. 평균만 요청받아도 중위수를 같이 붙여서 보고한다.

### 7. 테이블을 읽는 순서 (가이드 §04)

1. **1행이 무엇 하나인가**를 먼저 확정한다. `purchase_event` 1행 = 결제 1건이지 결제 유저 1명이 아니다. "결제 유저 몇 명"과 "결제 몇 건"은 다른 질문이다.
2. **붙일 키가 있는지** 확인한다. 우리 스키마의 공통 키는 `UID`(유저), `session_id`(세션), `level_id`(레벨), `item_id`(아이템)다. 키가 없는 로그는 어떤 데이터와도 붙일 수 없다.
3. **로그인지 스냅샷인지** 구분한다. `*_event`는 일어난 일이 한 줄씩 쌓이는 로그(과거 재구성 가능), `user_property`는 그날의 상태만 찍는 스냅샷(그 사이 행동은 모름).
4. **기간을 반드시 건다.** 기간을 안 주면 전체 파티션을 스캔해 비용이 커진다.

### 9. 결과를 낼 때

- 숫자만 던지지 않는다. **어느 세그먼트에서 무엇이 달라졌는지** 한 줄로 지목한다.
- 스캔한 기간과 행 수를 함께 적는다.
- 규칙 view나 로그 요청서와 어긋나는 값이 나오면 **그 사실을 먼저 보고**한다. 임의로 보정하지 않는다.
